# Manifest-driven Bible sources

## Decision

Bible text is distributed and installed as JSON plus a companion manifest. The JSON files are the source of truth. SQLite is a disposable runtime cache generated by the Go `bible-rpc` sidecar for indexed lookup and FTS; no preseeded Bible content database is shipped.

The renderer continues to use the existing `bibleAPI`. Electron main remains the security boundary and forwards only `bible.*` JSON-RPC calls to the sidecar.

## Editions

- The public/free build stages every valid manifest and content file in `public-bibles`.
- The paid build stages the public set plus every valid source in `private-bibles`.
- Both builds use the same Electron Builder configuration. The Make build prepares the selected edition in `derived/bible`, which Electron Builder copies to `resources/bible`.
- The generated `bundle.manifest.json` identifies the edition and lists every packaged source. Packaging verification rejects missing, unlisted, duplicate, or private sources in a public bundle.

## On-disk layout

```text
resources/bible/
  bundle.manifest.json
  bible-runtime.sqlite

userData/bibles/
  packages/<downloaded Bible>.sqlite
  cache/bible-runtime.sqlite
  cache/bible-runtime.fingerprint
```

The raw JSON and source manifests are build-time inputs and are never shipped to users. Bundled files are read-only. Downloaded standalone SQLite packages can be added or removed from the packages directory; the sidecar detects the resulting package-set fingerprint on its next start.

## Build source manifest

Each repository manifest uses `ems.bible-manifest.v1` and supplies a stable ID, abbreviation, display name, language, revision, content filename, provenance, and attribution. These manifests drive the public/paid build but are not distributed.

```json
{
  "format": "ems.bible-manifest.v1",
  "id": "public:kjv",
  "abbreviation": "KJV",
  "name": "King James Version",
  "language": "en",
  "revision": "1",
  "contentFile": "KING JAMES BIBLE.json",
  "publicDomain": true,
  "copyright": "Public Domain",
  "copyrightInfo": "King James Version (KJV). Public Domain.",
  "infoUrl": ""
}
```

## Runtime behavior

The build pre-generates `bible-runtime.sqlite` for every public or paid bundle, then removes its staged JSON and source manifests. The sidecar can therefore open bundled Bibles immediately without parsing JSON or building FTS during first launch. JSON and manifests remain authoritative repository inputs; the shipped database is the runtime artifact.

With no downloaded packages, the sidecar uses the packaged cache directly. It scans `userData/bibles/packages` for `.sqlite` files downloaded from the portal. Each package must use the optimized Bible schema and include complete version attribution. When the package set changes, the sidecar validates the files and atomically generates a combined cache under user data, leaving both the packaged database and downloads untouched. Existing reference resolution, passage retrieval, attribution, and FTS operate on that cache.

Invalid packages fail closed. Downloaded databases must have the supported optimized schema, internally consistent chapter/verse data, and complete attribution. Installed abbreviations may not collide with bundled or other installed translations.

## Future management and web providers

Additive administration methods can later expose installation, removal, enable/disable, refresh, and source status without changing reading methods. Web providers should implement the same internal source contract and disclose capabilities such as passage, search, and offline availability. Credentials remain outside renderer code.
